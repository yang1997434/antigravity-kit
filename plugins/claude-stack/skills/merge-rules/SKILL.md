# 提交、推送、合并的规矩

只有主会话提交和推送；子代理不 commit、不 push，除非 brief 明写。部署不在这里，照全局规则「授权」一节：合并不等于上线。`git add <具体文件>`，不 `git add .`。

## 一、这个仓能不能不问就提交推送

1. 该仓 `AGENTS.md` / `CLAUDE.md` 或工作区总纲写了的，照它。
2. 没写的自己判：最近 90 天主干提交的作者只有用户一个人（`git log --since=90.days --format=%an <主干> | sort -u`），而且不是别人仓的 fork（`gh repo view --json isFork,parent`），就算「只有用户一个人在推」，可以不问。新建的仓默认算。
3. 不满足的，未经要求不 commit / push / 开 PR。

## 二、分档

按改动内容定，取最高的一档，拿不准按高的算。

- 只改文档、注释、测试、文案：跑改动命中的测试和 lint。
- 其余改动：本地全量门禁绿；改了用户可见流程的再过 `tester`。
- 碰计费、权限、支付、删除、迁移、并发事务边界或外部付费调用：另要 `reviewer` 对将要合并的那一版给出通过。门禁绿不等于这一档可以合。

该仓自己的门禁和部署分档写得更细的，照该仓。

## 三、先给用户看再提交的

CI 配置（`.github/workflows/`）、门禁脚本、部署脚本的改动。

## 四、结论只对那一版有效

`tester` / `reviewer` 通过后又改了代码：解冲突和小修派 `checker` 核对改动处并重跑命中的测试；改了行为的重新走一遍。写代码的不能只凭自己说「可以合」。

## 五、冲突

- 在自己的分支上 rebase 到最新主干，解完重跑命中的测试。
- 落在本批清单外的文件、lockfile、迁移上的，由主会话串行处理；lockfile 和生成物重新生成，不手工拼；不整文件选边。
- 同一分支第三次冲突就停下报告。

## 六、不为变绿放松检查

不跳过或删测试、不降阈值、不关检查。偶发失败只重跑一次，再红当真问题查。

## 七、推主干

- 推前 `git pull --rebase`；拉下来的提交碰了同一批文件就重跑命中的测试。
- 本地主干上有别的会话没推的提交，先不推，告诉用户。
- 主干上有检查在跑时等它跑完（新 push 会取消在跑的那次）。
- 不强推。推完读回远端，确认是这一版。
- 主干 CI 红了先 `git revert` 再修。

## 八、台账

每次回退、每次主干 CI 变红，当场在该仓续做文件 `<仓>-followups.md` 记一行：日期、哪次提交、原因。
